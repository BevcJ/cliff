Data Science and Machine Learning Roles

Widen job discovery and title filtering to include core Data Science and Machine Learning roles while preserving distinct canonical titles, role groups, and company-level classification data.

1. Overview

1.1 Problem Statement

The hiring radar currently treats a job as interesting when its title matches a configured AI execution or AI product role, or contains a broader AI signal. This intentionally excludes ordinary Data Science and Machine Learning jobs. As a result, titles such as Data Scientist, Machine Learning Engineer, and ML Engineer are either discarded by the ATS title prefilter or do not receive a useful canonical role label during normalization.

The prefilter and normalization stages are not separate taxonomies. All ATS collectors and normalizers call the shared functions in classify.py. The expansion therefore needs one central taxonomy change, followed by propagation of the new role groups through aggregation, exports, enrichment inputs, inspection snapshots, and database storage.

Reusing AI Execution Role would retain the jobs but would erase the distinction requested by the business. Broad keyword matching for data science or machine learning would create a different problem by admitting managers, research roles, MLOps, platforms, and other adjacent positions that have not been approved.

1.2 Proposed Solution

Add two narrow role families to the central taxonomy:

  • Data Scientist
  • Data Science Role
  • Machine Learning Engineer
  • Machine Learning Role
  • ML Engineer alias

The same matcher will admit these titles during collection prefiltering and normalization. Normalization will always emit canonical titles, so Senior ML Engineer becomes Machine Learning Engineer, never AI Engineer. Discovery will search the two canonical titles plus the approved ML Engineer alias.

Company aggregation will store every unique observed job role group in a new role_groups array. The existing scalar role_classification remains as a compatibility and display summary. Filtering by the array is deliberately deferred, but the array will be persisted as a first-class Postgres column so a later filter can use indexed array-overlap semantics.

1.3 Terminology

TermDefinition
Canonical titleThe normalized job title stored in job_title_normalized, for example Machine Learning Engineer.
Matching aliasAn alternative phrase accepted by the title matcher but normalized to a canonical title, for example ML Engineer.
Discovery termA phrase used to generate role-based search queries. Discovery terms are intentionally narrower than all matching aliases.
Role groupThe broad classification stored on a job, for example Machine Learning Role.
Company role groupsThe unique set of job role groups observed for a company in one processed collection.
First phraseThe known role phrase with the earliest start position in the normalized raw title.

2. Scope

In Scope

  • Data Scientist, including seniority or team modifiers around the canonical phrase.
  • Machine Learning Engineer, including seniority or team modifiers around the canonical phrase.
  • ML Engineer as a matching and discovery alias for Machine Learning Engineer.
  • Distinct job role groups for Data Science and Machine Learning.
  • All unique company role groups persisted in JSON and Postgres.
  • Reprocessing the latest complete retained raw ATS collection.

Explicitly Out of Scope

  • MLOps Engineer and ML platform roles.
  • Applied Scientist, Research Scientist, and ML Scientist.
  • Data Science Manager, Head of Data Science, and similar leadership-only titles.
  • Data Analyst, Data Engineer, BI, and generic analytics roles.
  • Generic discovery signals for data science or machine learning.
  • Inspection API or UI filters for the new role_groups array.
  • Board rediscovery or network recollection for the historical backfill.

3.1 Current Flow

  -> discovery queries
  -> is_ai_role_title_candidate(raw title)
       -> ATS detail fetch decision
       -> normalizer inclusion gate
  -> normalize_job_title()
  -> classify_role()
  -> dedupe and company aggregation
  -> exports and inspection snapshots

3.2 Proposed Flow

taxonomy.yaml
  -> canonical roles + matching aliases
  -> canonical roles + approved discovery aliases
  -> shared first-phrase matcher
       -> shared ATS prefilter
       -> shared normalization
       -> canonical title + distinct role group
  -> dedupe and company aggregation
       -> role_groups[]
       -> category title lists
  -> exports and inspection snapshots
  -> Postgres role_groups[]

3.3 Taxonomy Contract

The YAML structure will distinguish roles, aliases, and discovery aliases. This prevents plural or normalization-only aliases from automatically increasing query volume.

data_science_roles:
  - Data Scientist

machine_learning_roles:
  - Machine Learning Engineer

role_aliases:
  Machine Learning Engineer:
    - ML Engineer

discovery_role_aliases:
  - ML Engineer

TaxonomyConfig.all_roles remains the canonical role list. A separate discovery property combines canonical roles with approved discovery aliases. Alias validation must reject references to unknown canonical titles.

3.4 Matching and Precedence

  1. Clean and tokenize the raw title using the existing punctuation-insensitive phrase normalization.
  2. Apply the existing AI trainer exclusion before accepting any role match.
  3. Find every canonical role or matching alias present as a complete phrase.
  4. Select the match with the earliest phrase position in the raw title.
  5. If matches start at the same position, select the most specific match using phrase length.
  6. Return the canonical title and its configured role group.

3.5 Shared Prefilter and Normalization Gate

No provider-specific role lists will be introduced. Ashby, Greenhouse, Lever, Personio, Recruitee, SmartRecruiters, Teamtailor, and Workable already call is_ai_role_title_candidate() during collection metadata, detail-fetch selection, normalization, or all three. Expanding the central matcher changes all providers consistently.

Ashby, Recruitee, and Workable use this decision before requesting detail payloads. Future collections will therefore fetch details for the new role families. Historical raw collections may contain only listing-level data for jobs rejected by the old prefilter.

4.1 Company Summary Rules

role_groups is the source of truth for multi-valued company classification. Values are emitted in a fixed role-group order for deterministic JSON and tests.

Known groups presentrole_classification
NoneUnclear AI Role
Exactly oneThat role group
AI Execution Role + AI Product RoleBoth Execution + Product
Any other combination of two or more known groupsMultiple Role Groups

An unclear role does not replace a known scalar summary, but it remains visible in role_groups when the company has both known and unclear jobs.

4.2 Postgres Storage

Add role_groups text[] not null default '{}' to inspection_company_snapshots and create a GIN index. The Python inspection sync writes the field and includes it in the compact detail payload. Existing rows remain valid through the empty-array default.

This feature does not alter the inspection filter RPCs or React filter rail. A later feature can use the indexed array column with overlap semantics to match companies containing any selected role group.

5. Impacted Modules

Taxonomy and Models

configs/taxonomy.yaml, config.py, and models.py gain the new canonical role lists, aliases, discovery terms, role groups, and mixed-company summary.

Classification

classify.py builds canonical and alias matches, records match position, and applies first-phrase precedence. normalizers/common/roles.py receives canonical results from the same matcher.

Discovery

cli.py uses canonical roles plus ML Engineer for role search generation and accepts the alias as a selected role term. Generic ATS signal terms remain unchanged.

Aggregation and Export

aggregate.py counts and groups the new roles. export.py includes new title columns and role sections without hiding mixed-company role data.

Enrichment and Inspection

Company enrichment inputs and records preserve the title lists and role groups. Inspection snapshots include the new fields and search text includes the new normalized titles.

Database

A new Supabase migration adds the array column and GIN index. inspection_db.py writes the new column during transactional snapshot replacement.

6. Edge Cases and Behaviour

EC-1: ML abbreviation

ML Engineer is accepted and normalized to Machine Learning Engineer. It is not stored as a separate canonical title or role group.

EC-2: Seniority and team modifiers

Titles such as Senior Data Scientist and Staff Machine Learning Engineer, Personalization match because the canonical phrase remains intact.

EC-3: Adjacent roles

Data Science Manager, MLOps Engineer, Applied Scientist, and Research Scientist remain rejected unless they independently contain an existing approved AI role or AI signal under current behavior.

EC-4: Multiple roles in one title

The first recognized phrase wins. This avoids category selection based on YAML ordering or phrase length and makes title order the deterministic employer-provided signal.

EC-5: Trainer exclusion

The existing AI trainer exclusion remains authoritative. Machine Learning Engineer - AI Trainer is rejected even though it contains a new canonical role.

EC-6: Deduplicated postings

Aggregation must preserve all role groups represented by merged posting metadata rather than keeping only the first non-unclear canonical candidate group.

EC-7: Missing historical details

Reprocessing retained raw data can recover listing-level jobs. It cannot recreate historical detail responses that Ashby, Recruitee, or Workable never fetched under the old prefilter. The backfill does not make network requests.

EC-8: Existing records

Inspection and enrichment readers treat missing new arrays as empty, so previously processed collections remain readable without rewriting all retained history.

7. User Stories and Acceptance Criteria

US-1: Capture core Data Science roles

As an operator, I want Data Scientist postings to pass collection and normalization so companies hiring this role appear in the radar.

Acceptance: Senior Data Scientist is accepted, normalizes to Data Scientist, and receives Data Science Role.

US-2: Capture core Machine Learning roles

As an operator, I want full and abbreviated Machine Learning Engineer titles to be captured under one canonical role.

Acceptance: Machine Learning Engineer and ML Engineer both normalize to Machine Learning Engineer with Machine Learning Role.

US-3: Avoid relabeling as AI Engineer

As an operator, I want new role families labeled distinctly so Data Science and Machine Learning demand is not merged into existing AI execution reporting.

Acceptance: New canonical titles never normalize to AI Engineer unless the raw title's first recognized phrase is an existing AI role.

US-4: Preserve every company role group

As an operator, I want every unique role group observed for a company stored so later filtering can select companies containing any desired group.

Acceptance: A company with AI Product, Data Science, and Machine Learning jobs stores all three values once in role_groups.

US-5: Control search noise

As an operator, I want discovery widened only to approved job titles so query cost and irrelevant board results remain controlled.

Acceptance: Generated role queries include Data Scientist, Machine Learning Engineer, and ML Engineer, but not generic field phrases or adjacent roles.

US-6: Reprocess retained data manually

As an operator, I want a local command that applies the new taxonomy to already stored raw ATS responses without discovering or collecting boards again.

Acceptance: The provided process command reads retained files and rewrites only derived processed outputs.

8. Decisions Made

D-1: Two distinct role groups

Use Data Science Role and Machine Learning Role. A combined Data/ML group was rejected because it would prevent separate reporting; reusing AI Execution was rejected because it would erase the requested distinction.

D-2: Narrow core IC scope

Initially accept only Data Scientist and Machine Learning Engineer titles, plus the ML Engineer alias. A broader technical family and unrestricted keyword matching were rejected due to ambiguity and collection noise.

D-3: Separate matching and discovery aliases

Do not make every accepted spelling a search term. Discovery is limited to canonical titles plus the approved ML abbreviation, which allows normalization aliases to grow later without silently increasing query count.

D-4: First recognized phrase wins

Resolve mixed titles by source-title order. Longest phrase and taxonomy-order precedence were rejected because they can override the role the employer presents first.

D-5: Store company role groups as an array

Add role_groups while retaining role_classification. Dynamic joined labels were rejected because combinations multiply and are poor filter keys; a single prioritized group was rejected because it loses data.

D-6: Defer filtering

Persist and index role_groups now, but do not change Supabase RPC filters or the React UI in this feature. This keeps the taxonomy expansion independently reviewable.

D-7: Manual raw-only backfill

Provide a processing command for the latest complete retained collection. Do not run board discovery, collection, extraction, enrichment, database sync, or generated-data backfill as part of implementation.

10.2 Manual Backfill

The latest complete retained ATS collection is 2026-07-03. Implementation will return the following command to the operator but will not execute it:

uv run ai-hiring-radar process --date 2026-07-03

The command reads data/raw/ats/2026-07-03/ and regenerates data/processed/job_candidates_2026-07-03.jsonl and data/processed/companies_2026-07-03.jsonl. It does not run discovery or make collection requests.

If the operator later chooses to publish the regenerated records to inspection after applying the migration, the separate command is:

uv run ai-hiring-radar sync-inspection-db --date 2026-07-03

11. Upgrade Paths

11.1 Role-group inspection filter

Add Supabase array-overlap filtering, filter options derived from role_groups, and a React multi-select after the stored taxonomy has been validated with real collections.

11.2 Expanded technical taxonomy

Evaluate MLOps Engineer, Applied Scientist, Research Scientist, ML Scientist, and leadership roles using observed false-negative data rather than broad assumptions.

11.3 Multi-valued job classification

Store multiple role groups on a single job if first-phrase precedence proves too lossy for hybrid titles. This requires a larger candidate contract change and is not needed for the initial expansion.

11.4 Historical detail recollection

Recollect selected boards only if listing-level historical records prove insufficient. This must use a new collection date rather than rewriting historical raw responses with current network data.
